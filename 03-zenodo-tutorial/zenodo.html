Why Archive?

  • GitHub is not an archive. Repos get renamed, moved, made private, or deleted.
  • DOIs make your work citable, including data, materials, code, and protocols, not just papers.
  • Funders and journals increasingly ask for persistent identifiers.
  • OSF has changed. Many networks need a new home for files and DOIs.

A DOI is a promise: this link will still work, and this version won’t change.

What Is Zenodo?

  • A general-purpose repository run by CERN
  • Free to use, and the software is open source (InvenioRDM)
  • Accepts any research output: data, code, slides, posters, protocols, preprints
  • Up to 50 GB and 100 files per record
  • Every record gets a DOI

zenodo.org

Log in with ORCID, GitHub, or an email account

Point out that you can sign in with ORCID or GitHub, which saves creating yet another account. A one-time increase to 200 GB per record can be requested if needed.

Key Idea: Records and Versions

Concept DOI

“All versions”

Always points to the latest

→

v1.0

Version DOI

→

v1.1

Version DOI

→

v2.0

Version DOI

  • Each record is one thing you archive. Each version gets its own DOI.
  • The concept DOI ties all the versions together.
  • Need a change? Make a new version, not a new record.

Which DOI to cite: the version DOI when you need the exact files (e.g., the analysis in a paper); the concept DOI when you mean “this project, whatever the latest is.” Files in a published version can’t be changed; that’s the point.

Key Idea: Access Options

Open

Anyone can download the files

Restricted

People request access and you approve

Embargoed

Files open up automatically on a date you pick

The description is always public, even when the files aren’t.

Restricted is useful for sensitive data in multi-site projects: the record is findable and citable, but you control who gets the files. Pick a license too (e.g., CC-BY 4.0 for data and materials, MIT for code).

Route 1: Upload Directly

Uploading Files, Step by Step

  1. Click New upload
  2. Drag in your files
  3. Answer “Do you already have a DOI?” → No (Zenodo reserves one for you)
  4. Fill in the description:
    • Resource type (dataset, software, presentation…)
    • Title, creators (with ORCIDs), description
    • License
  5. Choose access (open, restricted, embargoed)
  6. Publish

Warn the audience: once you publish, you can’t swap the files. Double-check before publishing, or make a new version.

Every new GitHub release becomes a new version of the same Zenodo record.

Releases were covered in the GitHub pre-conference workshop (recording: youtu.be/GCKf3qF0a_0). A release is a snapshot of your repo at a point in time, with a tag like v1.0.0.

Connecting GitHub, Step by Step

In Zenodo:

  1. Log in, then open your profile menu → GitHub
  2. Click Sync now
  3. Find your repository and flip the switch to on

In GitHub:

  1. Go to your repo → Releases → Draft a new release
  2. Add a tag (e.g., v1.0.0), a title, and notes
  3. Click Publish release

Back in Zenodo: wait a few minutes, then find your new DOI on the GitHub page.

The repo has to be switched on before you publish the release; releases made earlier won’t be archived. Only published releases count, not drafts.

Describe It: CITATION.cff

Add a CITATION.cff file to your repo so Zenodo (and GitHub) know how to cite it:

cff-version: 1.2.0
title: "Example BTS Project: Shared Analysis Code"
version: 1.0.0
license: "MIT"
type: software
message: "If you use this, please cite it as below."
authors:
  - given-names: Erin M.
    family-names: Buchanan
    affiliation: Harrisburg University
    orcid: "https://orcid.org/0000-0002-9689-4189"
  - given-names: "[Next]"
    family-names: "[Author]"
keywords:
  - big team science

Bonus: GitHub shows a “Cite this repository” button.

Make one at the citation file format initializer: citation-file-format.github.io/cff-initializer-javascript. Validate with cffconvert before releasing.

Or: .zenodo.json

More control: contributors, funding, communities, and links to your paper. If both files exist, Zenodo uses only .zenodo.json.

{
  "title": "Example BTS Project: Shared Analysis Code",
  "upload_type": "software",
  "license": "mit",
  "creators": [
    {"name": "Buchanan, Erin M.",
     "affiliation": "Harrisburg University",
     "orcid": "0000-0002-9689-4189"}
  ],
  "contributors": [
    {"name": "Site Lead, Example", "type": "DataCollector"}
  ],
  "related_identifiers": [
    {"identifier": "https://doi.org/[paper DOI]",
     "relation": "isSupplementTo",
     "resource_type": "publication-article"}
  ],
  "communities": [{"identifier": "[your-network]"}]
}

When It Doesn’t Work

  • No record appeared? Check the repo was switched on before the release, and that the release was published (not a draft).
  • Release failed? In Zenodo’s GitHub page, click the release, then Errors. It’s usually the metadata.
  • Bad CITATION.cff? Validate it with cffconvert first.
  • Wrong authors or title? Fix the metadata file, then publish a new release.

Tips for Big Teams

Zenodo for Big Team Science

  • Make a Zenodo Community for your network to collect every project’s outputs in one place
  • Get everyone’s ORCID before you publish, because author lists are long
  • Link everything with related identifiers: preprint ↔︎ data ↔︎ code ↔︎ materials
  • One record per output, with new versions when things change
  • Use restricted access for sensitive data so it’s citable but controlled
  • Add your funder (e.g., SSHRC grant) in the metadata

tenzing can help collect contributor names, affiliations, and ORCIDs up front. Communities can be curated, so a network can review what gets added.
