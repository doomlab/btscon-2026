Why Archive?

  • Get credit for everything you make: data, materials, code, and protocols, not just papers
  • Funders and journals increasingly ask for persistent identifiers (DOIs)
  • OSF has changed, so many networks need a new home for files and DOIs
  • Links break: websites and repos get renamed, moved, or deleted, but a DOI keeps working

What Is Zenodo?

  • A general-purpose repository run by CERN
  • Free to use, and the software is open source (InvenioRDM)
  • Accepts any research output: data, code, slides, posters, protocols, preprints
  • Up to 50 GB and 100 files per record
  • Every record gets a DOI
  • Log in at zenodo.org with ORCID, GitHub, or an email account

Point out that you can sign in with ORCID or GitHub, which saves creating yet another account. A one-time increase to 200 GB per record can be requested if needed.

→

v1.1

Version DOI

→

v2.0

Version DOI

  • Each record is one thing you archive. Each version gets its own DOI.
  • The concept DOI ties all the versions together.
  • Need a change? Make a new version, not a new record.

See it in action: jaspSyntheticData has v0.1.0 and v0.2.0 under one concept DOI.

Which DOI to cite: the version DOI when you need the exact files (e.g., the analysis in a paper); the concept DOI when you mean “this project, whatever the latest is.” Files in a published version can’t be changed; that’s the point.

Key Idea: Locked Files, Editable Descriptions

Files: locked 🔒

After you publish, files can’t be added, removed, or swapped. New files = new version.

Description: editable ✏️

Fix the title, authors, description, or links any time, with no new version needed.

Why that’s good:

  • Preregistrations and protocols get a permanent timestamp
  • Every version stays exactly as it was, so changes are traceable
  • The description grows with the project: add the paper, data, and code links later

Fixing a typo in the title or adding an author doesn’t need a new version. If someone uploads sensitive data by mistake, contact Zenodo support; they can help in exceptional cases. For preregistrations specifically, the locked files are the whole point: reviewers can check the plan against the paper.

Key Idea: Access Options

Choose who can download the files:

Open

Anyone can download the files

Restricted

People request access and you approve

Embargoed

Files open up automatically on a date you pick

The description is always public, even when the files aren’t.

Restricted is useful for sensitive data in multi-site projects: the record is findable and citable, but you control who gets the files. Pick a license too (e.g., CC-BY 4.0 for data and materials, MIT for code).

Share Links for Peer Review

Give reviewers access without making anything public:

Can view

Restricted or embargoed files of a published record

Can preview draft

A record you haven’t published yet

Can edit

Collaborators who help fill in the draft

  1. Open your record or draft and click Share
  2. Go to the Links tab
  3. Optional: add a title and an expiration date
  4. Pick the permission, then click Create a new link
  5. Copy the link and send it (e.g., in your journal submission)

Delete the link from the same tab whenever you want to turn off access.

A link works for all current and future versions of the record. For a journal submission, a “Can preview draft” link lets reviewers see the materials before you publish; once the paper is accepted, publish the record and its DOI goes live. Set an expiration date so access doesn’t linger.

Route 1: Upload Directly

Upload: Basic Information

  1. Go to My dashboard (top menu), then click New upload
  2. Files: drag in your files
  3. Basic information:
    • Digital Object Identifier: “Do you already have a DOI?” → No
    • Resource type: dataset, software, presentation…
    • Title and publication date
    • Creators: everyone in the citation, with ORCIDs
    • Description: what’s in the files and how to use them
    • Licenses: CC BY 4.0 by default. Help choosing: Creative Commons chooser or choosealicense.com for code

Once you publish, you can’t swap the files. Double-check before publishing, or make a new version. CC BY 4.0 is a good default for data and materials; MIT is common for code.

Upload: Recommended Info & Related Works

  1. Recommended information:
    • Contributors: helped, but not in the citation. Each needs a role (e.g., data collector)
    • Keywords and subjects: your own, or from EuroSciVoc or MeSH
    • Languages, version, and publisher
  2. Related works: link the paper, preprint, preregistration, or repo
    • Pick a relation (e.g., “Is supplement to”) and paste the DOI or URL
  3. Choose access (open, restricted, embargoed), then Publish

Zenodo’s form has more sections too (funding, alternate identifiers, references, and more), but these are the most important ones to fill in.

Creators vs contributors for big teams: creators are the author list that shows up when someone cites the record; contributors get credit on the record page but not in the citation (e.g., site research assistants, translators). Contributor roles come from the DataCite vocabulary. Related works are what tie a project together: the data record “Is supplement to” the paper, the code “Is supplement to” the data, and so on.

Add links as they appear: when the paper is published, edit the record and add its DOI. No new version needed.

Zenodo passes these links to DataCite along with the DOI, so indexes and other services can connect your outputs: someone who finds the paper can find the data, and vice versa. Do it in both directions where you can: put the data DOI in the paper’s data availability statement, and the paper DOI in the data record. This is where the editable-description idea pays off.

Every new GitHub release becomes a new version of the same Zenodo record.

Real example to show: jaspSyntheticData (doi.org/10.5281/zenodo.23075931), archived from GitHub releases v0.1.0 and v0.2.0 of github.com/doomlab/jasp-synthetic-data. Releases were covered in the GitHub pre-conference workshop (recording: youtu.be/GCKf3qF0a_0). A release is a snapshot of your repo at a point in time, with a tag like v1.0.0.

Connecting GitHub, Step by Step

In Zenodo:

  1. Log in, then open your profile menu → GitHub
  2. Click Sync now
  3. Find your repository and flip the switch to on

In GitHub:

  1. Go to your repo → Releases → Draft a new release
  2. Add a tag (e.g., v1.0.0), a title, and notes
  3. Click Publish release

Back in Zenodo: wait a few minutes, then find your new DOI on the GitHub page.

The repo has to be switched on before you publish the release; releases made earlier won’t be archived. Only published releases count, not drafts.

Describe It: CITATION.cff

Add a CITATION.cff file to your repo so Zenodo (and GitHub) know how to cite it:

cff-version: 1.2.0
title: "Example BTS Project: Shared Analysis Code"
version: 1.0.0
license: "MIT"
type: software
message: "If you use this, please cite it as below."
authors:
  - given-names: Erin M.
    family-names: Buchanan
    affiliation: Harrisburg University
    orcid: "https://orcid.org/0000-0002-9689-4189"
  - given-names: "[Next]"
    family-names: "[Author]"
keywords:
  - big team science

Bonus: GitHub shows a “Cite this repository” button.

Make one at the citation file format initializer: citation-file-format.github.io/cff-initializer-javascript. Validate with cffconvert before releasing.

Or: .zenodo.json

More control: contributors, funding, communities, and links to your paper. If both files exist, Zenodo uses only .zenodo.json.

{
  "title": "Example BTS Project: Shared Analysis Code",
  "upload_type": "software",
  "license": "mit",
  "creators": [
    {"name": "Buchanan, Erin M.",
     "affiliation": "Harrisburg University",
     "orcid": "0000-0002-9689-4189"}
  ],
  "contributors": [
    {"name": "Site Lead, Example", "type": "DataCollector"}
  ],
  "related_identifiers": [
    {"identifier": "https://doi.org/[paper DOI]",
     "relation": "isSupplementTo",
     "resource_type": "publication-article"}
  ],
  "communities": [{"identifier": "[your-network]"}]
}

When It Doesn’t Work

  • No record appeared? Check the repo was switched on before the release, and that the release was published (not a draft).
  • Release failed? In Zenodo’s GitHub page, click the release, then Errors. It’s usually the metadata.
  • Bad CITATION.cff? Validate it with cffconvert first.
  • Wrong authors or title? Fix the metadata file, then publish a new release.

Tips for Big Teams

Zenodo for Big Team Science

  • Make a Zenodo Community for your network to collect every project’s outputs in one place
  • Get everyone’s ORCID before you publish, because author lists are long
  • Link everything with related identifiers: preprint ↔︎ data ↔︎ code ↔︎ materials
  • One record per output, with new versions when things change
  • Use restricted access for sensitive data so it’s citable but controlled
  • Add your funder (e.g., SSHRC grant) in the metadata

tenzing can help collect contributor names, affiliations, and ORCIDs up front. Communities can be curated, so a network can review what gets added.
